===============================================================================
  1.  RESUME POUR DECIDEUR
===============================================================================

  CASAVEN7 est un fichier HTML statique unique. Pas de serveur, pas de base de
  donnees, pas d'API. Le studio 3D est du three.js procedural, et le paiement
  est un lien profond wa.me : la commande ne quitte jamais le navigateur tant
  que le client n'envoie pas lui-meme son message WhatsApp. Comptes, wishlists,
  commandes et avis vivent tous dans le localStorage, sur la machine du client.

  Cette architecture elimine d'office la majorite du Top 10 OWASP (pas de SQL,
  pas de SSRF, pas d'upload, pas de CSRF). Elle concentre le vrai risque en
  deux points : CE QUI EST ECRIT dans le localStorage, et CE QUI EN EST
  REAFFICHE.

  Le cote affichage etait deja correct. L'auteur avait ecrit un helper
  escapeHTML() et l'appliquait aux avis et aux commandes. Les tentatives
  d'injection par le formulaire d'avis ont ete rejetees pendant les tests.

  Le cote ecriture, lui, ne l'etait pas : TOUS LES MOTS DE PASSE DES MEMBRES
  ETAIENT STOCKES EN CLAIR, lisibles avec une seule ligne dans la console.

  Deux failles ont ete confirmees par exploitation reelle, pas par lecture :

    STOCKAGE EN CLAIR (CRITIQUE)
                     JSON.parse(localStorage.casaven7_users_v2) renvoyait
                     chaque identifiant avec son mot de passe en clair.

    DENI DE SERVICE CLIENT STOCKE (ELEVEE)
                     Une seule entree malformee (null) dans le wishlist faisait
                     planter renderWishlist() et AVORTAIT TOUT LE HANDLER
                     'load' : plus de grille produits, plus de studio 3D, plus
                     d'avis, plus de panier. La boutique s'affichait vide.
                     Reproduit en direct. C'est la seule faille qui met
                     l'application hors service.

  Les huit failles confirmees sont corrigees. Une suite de 34 tests de
  regression (SECURITY_TESTS.js) passe 34/34 sur le fichier patche ; lancee sur
  la copie d'avant patch elle remonte 16 echecs puis plante, parce que
  l'application non patchee est deja morte a ce stade.

  LE POINT HONNETE : l'application est nettement plus difficile a abuser, mais
  des comptes cote client ne sont PAS de l'authentification. Voir section 6,
  "Authentification cote client". C'est la seule chose impossible a corriger
  dans un fichier statique, et il ne faut pas la maquiller.

  Tout ce qui est a l'interieur se fait mutuellement confiance. Le point
  d'entree 4 est donc le plus important -- et c'est celui auquel le code
  d'origine faisait le plus confiance.

  1.  STOCKAGE DE MOTS DE PASSE EN CLAIR                          [ CRITIQUE ]
      Plaintext Storage of a Password
      CWE-256 / CWE-312  .  OWASP A02:2021 Cryptographic Failures
-------------------------------------------------------------------------------

  OU : handler d'inscription (ligne 2969 avant patch) et de connexion (2995).

  CODE AVANT PATCH

      const newUser = { username, password, orders: [], ... };
      users.push(newUser);
      writeJSON(STORAGE_KEYS.USERS, users);

      // ...et la connexion comparait directement :
      const matched = users.find((u) =>
        u.username.toLowerCase() === username.toLowerCase()
        && u.password === password);

  EXPLOITATION -- aucun acces particulier, aucune chaine d'exploit :

      JSON.parse(localStorage.casaven7_users_v2)
        .map(u => u.username + ':' + u.password)
      // -> ["yassine_casa:Soufiane2024", ...]

  Quiconque peut executer une ligne de JavaScript sur cette origine lit tous
  les mots de passe : la personne devant un poste partage ou familial, une
  extension de navigateur, quiconque recoit un telephone deverrouille, une
  image forensique du disque, ou n'importe quelle XSS future.
  CONFIRME PAR EXECUTION.

  IMPACT -- le vrai degat est AILLEURS. La reutilisation de mot de passe est la
  norme, et un mot de passe CASAVEN7 divulgue est souvent celui de la boite
  mail ou de l'Instagram du client. La fuite ne s'arrete pas a la boutique.

  CORRECTION  (casaven74 (3).html:1304-1380)
  PBKDF2-SHA256 via WebCrypto : 210 000 iterations, sel aleatoire de 128 bits
  par compte, cle derivee de 256 bits, le tout encode en hexadecimal. Le champ
  "password" a disparu.

      const PBKDF2_ITERATIONS = 210000;

      async function derivePassword(password, saltHex, iterations) {
        const salt = saltHex ? hexToBytes(saltHex)
                             : crypto.getRandomValues(new Uint8Array(16));
        const keyMaterial = await crypto.subtle.importKey(
          'raw', new TextEncoder().encode(password), 'PBKDF2', false,
          ['deriveBits']);
        const bits = await crypto.subtle.deriveBits(
          { name: 'PBKDF2', salt, iterations: iter, hash: 'SHA-256' },
          keyMaterial, 256);
        return { salt: bytesToHex(salt), iterations: iter, hash: bytesToHex(bits) };
      }

  Trois decisions deliberees :

    * LES COMPTES EXISTANTS SONT MIGRES, PAS CASSES.  upgradeLegacyUser()
      verifie une derniere fois l'ancien mot de passe en clair, le remplace par
      un hash sale et supprime le champ. Aucun client n'est bloque.  (:1357)

    * AUCUNE DEGRADATION SILENCIEUSE.  Si crypto.subtle est indisponible,
      l'inscription REFUSE avec un message clair au lieu de retomber
      discretement sur du clair. Un controle de securite qui se degrade sans le
      dire est pire que pas de controle du tout.

    * COMPARAISON A TEMPS CONSTANT  (digestEqual, :1338) : pas de sortie
      anticipee qui revelerait combien de caracteres correspondent.

  TESTS : 8 tests -- forme de l'enregistrement, absence de clair n'importe ou
  dans le storage, mot de passe correct et incorrect, utilisateur inconnu,
  migration d'un compte legacy, et compte migre refusant toujours un mauvais
  mot de passe.

  >>> PORTEE DE CE CORRECTIF -- A LIRE.  Le hashage empeche le localStorage
  >>> d'etre un annuaire de mots de passe lisible. Il NE transforme PAS ceci en
  >>> authentification. Voir section 6, "Authentification cote client".

  2.  CONTENT SECURITY POLICY ABSENTE                               [ ELEVEE ]
      Missing Content Security Policy
      CWE-693 Protection Mechanism Failure
      OWASP A05:2021 Security Misconfiguration
-------------------------------------------------------------------------------

  OU : <head> -- ni CSP, ni politique de referrer (lignes 1-50 avant patch).

  POURQUOI C'EST IMPORTANT
  La CSP est ce qui limite les degats APRES qu'autre chose a mal tourne. Sans
  elle, tout script qui atteint la page -- par un CDN compromis (code tiers sans controle d'integrite), une
  extension malveillante, ou une injection future -- peut charger du code
  depuis n'importe ou et envoyer le contenu du localStorage vers le serveur
  d'un attaquant. Avec une politique stricte, le meme script injecte peut
  s'executer mais ne peut ni telecharger sa charge utile ni rien exfiltrer.

  CORRECTION  (casaven74 (3).html:12)

      default-src 'self'; base-uri 'none'; object-src 'none';
      form-action 'none'; frame-src 'none'; worker-src 'none';
      manifest-src 'none';
      script-src 'self';
      style-src  'self' https://fonts.googleapis.com;
      font-src   https://fonts.gstatic.com;
      img-src    'self' data: blob:;
      connect-src 'self'

  Plus <meta name="referrer" content="strict-origin-when-cross-origin"> et
  referrerpolicy="no-referrer" sur les deux balises CDN, pour ne pas divulguer
  le parcours de navigation a des tiers.

  VERIFIE EN DIRECT, PAS SUPPOSE. Chaque directive a ete testee en essayant de
  la violer :

      Attaque tentee                                          Resultat
      ------------------------------------------------------  --------
      <script src="https://cdn.jsdelivr.net/..."> injecte      BLOQUE
      fetch() vers une origine tierce                          BLOQUE
      detournement par <base href="https://cdn.jsdelivr.net/"> BLOQUE
      eval() d'une chaine                                      BLOQUE
                                              (pas de 'unsafe-eval')

  L'URL hors liste blanche utilisee dans le test est volontairement un CDN
  JOIGNABLE. Une premiere version utilisait evil.example.com, qui ne resout
  pas : ces tests passaient sur une page SANS AUCUNE CSP, pour la mauvaise
  raison. Le test peut maintenant reellement reussir, donc un "pass" veut dire
  quelque chose.

  NI 'unsafe-inline' NI 'unsafe-eval'. La premiere version de cette politique
  portait encore 'unsafe-inline' dans script-src ET style-src, parce que la
  config Tailwind, les ~2 000 lignes de l'application et la feuille de style
  etaient toutes inline. Elles ont depuis ete extraites dans app.js et
  styles.css (section 8) : la politique refuse desormais purement et simplement
  un <script> inline injecte et un attribut style= injecte. Les deux sont
  couverts par des tests.

  4.  CODE TIERS CHARGE SANS CONTROLE D'INTEGRITE (SRI absent)    [ MOYENNE ]
      Download of Code Without Integrity Check
      CWE-494 / CWE-829  .  OWASP A08:2021 Software and Data Integrity Failures
-------------------------------------------------------------------------------

  OU : <head>, lignes 14 et 49 avant patch.

      <script src="https://cdn.tailwindcss.com"></script>        <!-- non versionne -->
      <script src="https://cdnjs.cloudflare.com/.../three.min.js"></script>  <!-- sans SRI -->

  Les deux scripts s'executent avec un acces complet au DOM et au localStorage.
  Ce que renvoient ces URL est accorde une confiance totale. L'URL Tailwind est

  modification ici.

  CORRECTION (three.js)  (casaven74 (3).html:63)
  Subresource Integrity -- le navigateur hashe le fichier telecharge et refuse
  de l'executer en cas de difference.

      <script src="https://cdnjs.cloudflare.com/ajax/libs/three.js/r128/three.min.js"
        integrity="sha384-CI3ELBVUz9XQO+97x6nwMDPosPR5XvsxW2ua7N1Xeygeh1IxtgqtCkGfQY9WWdHu"
        crossorigin="anonymous" referrerpolicy="no-referrer"></script>

  CORRECTION PARTIELLE (Tailwind) -- ET UNE TENTATIVE QUI A ECHOUE.
  L'URL est desormais figee sur 3.4.16, donc une nouvelle version majeure ne
  peut plus arriver sans prevenir. Le SRI a ete tente puis ANNULE :

      Access to script at 'https://cdn.tailwindcss.com/3.4.16' has been blocked
      by CORS policy: No 'Access-Control-Allow-Origin' header is present on the
      requested resource.

  integrity= exige une reponse compatible CORS. cdn.tailwindcss.com n'envoie
  aucun en-tete Access-Control-Allow-Origin : ajouter integrity + crossorigin
  empeche le script de se charger et le site s'affiche sans aucun style.
  DETECTE DANS LE NAVIGATEUR, PAS SUPPOSE. Le pin de version est conserve ; le
  trou d'integrite est reel et consigne en section 6, "Dependance tierce non verifiable". La vraie correction est de
  compiler Tailwind au build et de l'heberger soi-meme -- le CDN de Tailwind
  affiche lui-meme dans la console "should not be used in production".

  5.  EXIGENCES DE MOT DE PASSE INSUFFISANTES                     [ MOYENNE ]
      Weak Password Requirements
      CWE-521  .  OWASP A07:2021 Identification and Authentication Failures
-------------------------------------------------------------------------------

  OU : handler d'inscription (2953 avant patch) et markup (830, 836).

      <input id="signup-password" required minlength="4"
             placeholder="Create a password (min 4 chars)">

  Minimum de 4 caracteres, aucune regle de jeu de caracteres sur

  CORRECTION  (casaven74 (3).html:3081-3137)
  Identifiant ^[A-Za-z0-9_.\-]{3,24}$ ; mot de passe 8 a 128 caracteres ; le

  navigateur. Les attributs HTML sont un confort ; les controles JavaScript
  sont la vraie barriere.

  DEUX CONSEQUENCES CONCRETES, atteignables sans aucun privilege :

    1. LE LIEN DE COMMANDE CASSE SILENCIEUSEMENT.  Le lien WhatsApp embarque
       toute la commande en query string URL-encodee. En montant assez haut la
       quantite, l'URL wa.me depasse ce que les navigateurs et WhatsApp
       acceptent. Le bouton a toujours l'air normal et cesse simplement de
       fonctionner : un bug de chiffre d'affaires tres difficile a
       diagnostiquer depuis un signalement client.

    2. SATURATION DU STOCKAGE.  Les avis sont persistes sans plafond de nombre
       ni de longueur. Remplir le quota d'origine (~5 Mo) fait echouer
       writeJSON -- et l'erreur est avalee par un catch vide, donc wishlists et
       commandes cessent d'etre enregistrees sans le moindre message.

  CORRECTION  (casaven74 (3).html:1304-1312)
  Quantite <= 99 par ligne . avis stockes <= 200 . commentaire <= 600
  caracteres (applique en JS ET via maxlength) . identifiant <= 24 .
  wishlist <= 100 entrees.

  TESTS : 150 clics synthetiques sur "+" s'arretent a 99 ; le lien profond
  reste sous 2 000 caracteres ; 500 avis injectes sont ramenes a 200 ; un
  commentaire de 5 000 caracteres est stocke a exactement 600.

  8.  POINT D'INJECTION XSS STOCKEE (interpolation non echappee)   [ FAIBLE ]
      Stored Cross-Site Scripting

-------------------------------------------------------------------------------

  OU : syncAccountUI(), ligne 2238 avant patch.

      <span class="...">${ord.total} DH</span>
      // tous les champs voisins passaient par escapeHTML() -- pas celui-la

  L'auteur echappait ord.summary et ord.date sur les deux lignes juste

  AUTHENTIFICATION COTE CLIENT                      [ CRITIQUE / ARCHITECTURAL ]
  Use of Client-Side Authentication
  CWE-603 / CWE-602  .  OWASP A07:2021
       LES COMPTES SONT DECORATIFS, PAS DE L'AUTHENTIFICATION

       Tout vit dans le localStorage, sur la machine du visiteur : le visiteur
       est donc des deux cotes du controle. Une ligne suffit pour prendre
       n'importe quelle identite :

           localStorage.setItem('casaven7_session_v2', '"quelqu_un_dautre"');
           // -> connecte sous son identite

       L'historique de commandes peut etre invente, les avis marques
       verified: true, et chaque enregistrement de compte peut etre lu. Le hashage a
       supprime l'ANNUAIRE DE MOTS DE PASSE ; il n'a pas cree -- et ne peut pas
       creer -- une frontiere de confiance qui n'existe pas.

       >>> Traiter ces comptes comme un CONFORT PAR NAVIGATEUR -- une wishlist
       >>> sauvegardee et un historique local -- et rien de plus. N'y rattacher
       >>> aucune valeur : pas de reduction, pas d'avoir, pas de tarif membre,
       >>> aucune donnee personnelle au-dela de ce que le client taperait de
       >>> toute facon dans un message WhatsApp.

       VRAIE CORRECTION : un backend qui possede les comptes, les sessions
       (cookies HttpOnly + Secure + SameSite=Lax), les commandes et la
       limitation de debit. Hashage cote serveur avec Argon2id ou bcrypt. En
       attendant, ce risque est ouvert par conception.

       Consequence de l'authentification cote client, pas un defaut. Un client qui s'inscrit sur son

  EN-TETES HTTP DE SECURITE MANQUANTS                               [ MOYENNE ]
  Clickjacking CWE-1021  .  HSTS absent CWE-319  .  MIME sniffing CWE-430
  OWASP A05:2021 Security Misconfiguration
       ILS NE PEUVENT PAS VENIR D'UNE BALISE <meta>
       frame-ancestors (clickjacking), X-Content-Type-Options,
       Strict-Transport-Security et Permissions-Policy sont IGNORES dans une
       balise <meta> : les navigateurs ne les honorent qu'en vrais en-tetes de
       reponse.  LA CSP DU FICHIER NE PROTEGE DONC PAS CONTRE LE CLICKJACKING.
       A configurer sur le serveur web :

           add_header Content-Security-Policy "frame-ancestors 'none'" always;
           add_header X-Content-Type-Options    "nosniff" always;
           add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
           add_header Permissions-Policy        "camera=(), microphone=(), geolocation=()" always;

       Sur Netlify ou Vercel, la meme chose va dans _headers / vercel.json.


  DEPENDANCE TIERCE NON VERIFIABLE                                  [ RESOLU ]
  Download of Code Without Integrity Check  .  CWE-494  .  OWASP A08:2021
       Tailwind est desormais compile avec la CLI Tailwind et servi depuis
       styles.css, sur l'origine du site. La balise cdn.tailwindcss.com a ete
       supprimee : il ne reste plus aucun script tiers invérifiable. three.js
       est le seul script tiers restant, et il est verrouille par SRI.
       Voir section 3, point 4.


  COMPOSANT OBSOLETE                                                 [ RESOLU ]
  Use of Unmaintained Third-Party Components
  CWE-1104  .  OWASP A06:2021 Vulnerable and Outdated Components
       three.js est passe de r128 (2021) a r187 (octobre 2026) et est desormais
       servi depuis l'origine du site, dans vendor/three.module.min.js : il n'y
       a donc plus aucun hash SRI a maintenir.
       Deux ruptures d'API ont du etre traitees, toutes deux commentees dans

       outputColorSpace / texture.colorSpace (r152), et le facteur PI implicite

       garde exactement son apparence : une mise a jour de securite n'est pas

       Mesure contre le rendu de reference r128 : la luminance moyenne bouge de

  AUCUNE PROTECTION CONTRE LE BRUTE FORCE                            [ FAIBLE ]

       Sans serveur, cela n'a pas de sens : un attaquant avec un acces local

  CSP AFFAIBLIE PAR 'unsafe-inline'                                  [ RESOLU ]

  7.5  RELECTURE INDEPENDANTE DES MODIFICATIONS

  Relu comme le ferait un attaquant, en cherchant les faiblesses introduites
  par le correctif lui-meme :

    * sanitizeWishlist() n'EMET jamais que des valeurs {id, color} recopiees du
      catalogue : il ne peut pas transmettre de structure controlee par un
      attaquant en aval.

    * Inscription et connexion sont devenues async. Les deux desactivent le
      bouton de soumission le temps du traitement et le reactivent dans un
      finally : une exception ne peut pas laisser le formulaire mort, et une
      double soumission pendant les ~200 ms de derivation est impossible.

    * upgradeLegacyUser() relit le storage avant d'ecrire, au lieu de reecrire
      une copie memoire perimee : il ne peut pas ressusciter un compte
      supprime.

    * digestEqual() compare des empreintes hexadecimales de longueur fixe sans
      sortie anticipee.

    * La CSP a ete verifiee en tentant quatre violations, pas en relisant la
      chaine de caracteres.

    * UNE REGRESSION AUTO-INFLIGEE A ETE DETECTEE ET ANNULEE : le SRI sur le
      CDN Tailwind cassait la page (code tiers sans controle d'integrite). Trouvee en chargeant la page dans un
      navigateur. Elle n'aurait PAS ete trouvee en relisant le diff.

===============================================================================
  10.  CONCLUSION
===============================================================================

  Huit vulnerabilites confirmees sont corrigees et verifiees par une suite de
  regression qui echoue sur le fichier non patche. Deux des risques d'abord
  laisses ouverts -- le CDN Tailwind invérifiable et le 'unsafe-inline' de la
  politique -- ont depuis ete fermes en compilant Tailwind en local et en
  sortant tout le script et tout le style du HTML ; three.js est par ailleurs
  passe de r128 a r187 et auto-heberge. LA PAGE NE CHARGE PLUS AUCUN SCRIPT
  TIERS : script-src vaut 'self', sans 'unsafe-inline' ni 'unsafe-eval'. Deux failles ont ete
  prouvees par execution plutot que par deduction. Onze soupcons ont ete
  instruits puis ecartes comme faux positifs, et cinq risques restent ouverts
  avec la raison donnee pour chacun.

  CELA NE SIGNIFIE PAS QUE L'APPLICATION EST SECURISEE. Des tests qui passent
  montrent que les problemes corriges le restent ; ils ne disent rien de ce qui
  n'a pas ete cherche.

  Le risque dominant est l'AUTHENTIFICATION COTE CLIENT -- et il est architectural, pas accidentel : une
  page statique ne peut authentifier personne, et aucune quantite de code cote
  client n'y changera rien. Tout le reste de ce rapport est secondaire par
  rapport a cette seule decision.
